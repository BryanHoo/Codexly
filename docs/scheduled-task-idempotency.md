# 定时任务写接口幂等约定

创建、更新、删除、启停及立即运行接口必须携带非空 `Idempotency-Key`，缺失或空字符串返回 `400`。列表、事件订阅和预览不需要该请求头。内置客户端的写请求已自动携带该请求头；调用方重试同一次操作时必须复用原 key，新操作应生成新 key。

服务端统一使用 `runIdempotent`：

- 同一操作、同一任务及同一 key 的并发请求共享进行中的执行；成功后的重试复用首次响应内容和状态码，不再次写入或启动 Agent。
- 创建、更新和启停使用完整的已校验请求体生成指纹；同一作用域及 key 携带不同参数返回 `409 IDEMPOTENCY_CONFLICT`。创建的作用域为全局创建操作，更新、删除、启停和立即运行按操作及 `taskId` 隔离。删除和立即运行没有业务请求体，以 `{}` 作为指纹输入。
- 立即运行复用的是首次接受请求时的任务快照；即使后台运行已结束，重试也不会再次启动。读取当前状态应调用列表接口。
- 业务错误保持原有 `400`、`404`、`409` 映射；失败结果不缓存。失败可能发生于部分副作用之后，因此失败后重试不代表端到端“恰好一次”。进行中请求达到容量上限时返回 `503 IDEMPOTENCY_CAPACITY_EXCEEDED`。

## 有效范围与重启边界

幂等记录仅保存在当前 Server 实例的内存中。默认成功结果有效期为完成后 **10 分钟**，最多缓存 **1,000 条**，与其他使用该 runner 的接口共享容量；可通过 `idempotencyTtlMs`、`idempotencyCacheSize` 配置。容量淘汰可能提前结束保护。进行中请求不受成功结果 TTL 淘汰。

Server 关闭、进程崩溃或重启后，幂等记录丢失；多个 Server 实例之间也不共享记录。定时任务及运行历史的持久化不等于请求 key 的持久化，因此跨重启或缓存淘汰后的同 key 重试可能再次创建或执行任务。响应丢失且超出保护范围时，应先核对任务列表及运行历史，不能把盲目重试视为安全操作。

本约定采用请求标识、参数冲突校验和响应复用的接口设计原则，参考 [AWS：Making retries safe with idempotent APIs](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)。当前实现不承诺跨重启的持久化幂等或 Agent 工作的端到端恰好一次执行。
