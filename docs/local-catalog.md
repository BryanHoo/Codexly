# 本地目录与任务

Codexly 是目录、任务及其管理状态的唯一数据源。Web 和桌面端均使用应用自己的 SQLite 仓储；AI 引擎负责执行回合与保存其对话上下文。

## 设计依据

[Codex App Server](https://learn.chatgpt.com/docs/app-server) 提供 thread/start、thread/resume、thread/fork 和分页历史接口。[Claude Agent SDK](https://code.claude.com/docs/en/agent-sdk/sessions) 也通过独立 session ID 恢复会话。因此应用任务和引擎会话采用两种身份：应用 ID 用于路由、偏好、附件和事件；provider + sessionId 只用于执行适配器。

目录与任务元数据采用 SQLite，沿用项目已有的 Worker 与异步 I/O 边界。SQLite 的 [WAL](https://www.sqlite.org/wal.html) 支持读写并行；[外键约束](https://www.sqlite.org/foreignkeys.html) 与事务保证迁移、目录删除及任务归属的一致性。实现不复制引擎的整个 Thread JSON，不新增轮询同步。

## 数据与边界

| 数据                 | 权威位置                    | 规则                                                     |
| -------------------- | --------------------------- | -------------------------------------------------------- |
| 目录                 | managed_projects            | 一个应用 ID 对应一个规范化绝对路径，路径唯一             |
| 任务                 | managed_tasks               | 名称、目录归属、置顶、归档、更新时间和运行状态归应用管理 |
| 执行绑定             | 任务的 provider、session_id | 新任务独立生成 ID，首次执行才创建引擎会话                |
| 对话正文与执行上下文 | 对应引擎                    | 通过适配器按需读取、恢复和分叉                           |
| 导入标记             | managed_catalog_migration   | 与全部导入记录在同一事务提交                             |

Web 与桌面端在同一台电脑、同一系统用户下共用 `~/.codexly/state.sqlite3`，同时共用 `engines/claude` 历史投影目录。`CODEX_HOME` 和 `--codex-home` 仅决定 Codex 引擎的原生配置、会话位置及旧数据发现，不再决定应用数据位置。Codex、Claude 自身的配置与认证仍由官方引擎维护。

| 平台    | 应用数据目录             |
| ------- | ------------------------ |
| macOS   | `/Users/<用户>/.codexly` |
| Ubuntu  | `/home/<用户>/.codexly`  |
| Windows | `%USERPROFILE%\.codexly` |

Node 使用 [os.homedir()](https://nodejs.org/api/os.html#oshomedir)，桌面端使用 [Tauri homeDir](https://v2.tauri.app/reference/javascript/api/namespacepath/#homedir) 对应的原生接口，禁止拼接启动目录或通过系统应用数据目录创建第二份业务数据。引擎安装资源、操作系统登录服务登记、平台日志与可再生缓存仍遵循对应平台的专用目录。

两端共用 `packages/protocol/src/local-catalog-schema.json` 的表定义及 `app-storage-migration.json` 的导入 SQL。Web 数据库操作在 SQLite Worker 执行，桌面端在阻塞池执行；WAL、外键、5 秒 busy timeout 和短事务支持同机多进程访问，不增加后台同步轮询。切回窗口时，两端共用的恢复逻辑只使项目、任务、归档和置顶列表失效，后台不读取聊天正文。

### ACP 定时任务配置（开发中）

`acp_scheduled_configs` 独立保存计划的 ACP 原始配置，按 `source=web/desktop` 和原计划 ID 区分，避免两端同名计划互相覆盖。记录包含引擎、原始字符串或布尔选项及修订号；创建要求 `expectedRevision=0`，修改和删除要求匹配当前修订号，冲突返回空结果或 `false`。Node 和 Rust 共用 `packages/protocol/src/acp-scheduled-config-sql.json`，原子 SQL 同时约束数量和容量：最多 1000 项、单项选项 JSON 最多 256 KiB、总计最多 16 MiB。

此增量表不改变共享 `user_version`、旧表字段或旧计划 JSON；旧版仍读取原计划和运行记录。读取时重新校验 ACP 值，损坏配置明确失败，不自动使用全局默认配置。Web 在运行时明确声明 `runtime=acp` 时，使用所属来源的配置执行已有计划；缺少配置或 ACP 执行端口时在创建会话前失败，不转换旧模型或权限选项，也不写旧任务设置。原有附件恢复与持久提交认领继续使用。

已有运行的启动结果先于当前配置、目录和附件解析重放，恢复仅补写结果与清理原附件；配置更改、配置删除或项目不可用不能导致再次启动。结果未知时保留应用任务 ID 并阻止同一计划继续投递。

桌面已有计划在保存了 `desktop` 来源的显式 ACP 配置后使用 ACP 入口，其余计划暂时保留原执行入口。应用任务创建键和发送键均由项目及原 runId 确定；创建前在既有 `native_acp_submissions` 记录原指纹与尚未发送状态，发送仍通过现有 ACP 原生命令，复用附件授权与原始 `initialConfig`。不读取旧模型或写入旧任务设置，不通过 HTTP 绕行。

桌面重启时只检查中断运行及相关失败运行的私有阶段：确认启动的投影为 `started`，未知结果投影为 `failed`、保留任务引用并禁用计划，新版本还会阻止重新启用、改写或手工重发。旧文件继续使用原 schemaVersion 和四种运行枚举，不加入 `unknown` 或 `cleanup_pending`。私有账本损坏会明确失败，不能猜测成功或清除发送占用；普通完成历史和空闲调度不反复读取账本。ACP 计划编辑、新计划的私有保存及删除关联仍在迁移中，生产能力声明尚未切换。

## 应用目录升级

升级前退出旧版本的 Web 服务和桌面应用，再分别启动新版本。首次启动发现 `CODEX_HOME/codexly`、默认 `~/.codex/codexly` 和旧 Tauri 应用目录（macOS Application Support、Ubuntu XDG 数据目录、Windows Roaming AppData）。已经迁移的目录以目标数据库内的标记判断；不再反复导入旧记录。

- 若目标数据库尚不存在，使用 SQLite 的 [VACUUM INTO](https://www.sqlite.org/backup.html) 创建旧 Web 数据库的一致快照，包含 WAL 中已提交的数据。通过同目录临时文件和不覆盖目标的原子发布，避免并发启动替换已打开的数据库。
- 在共享事务内合并旧桌面目录与任务，并提交对应源目录的完成标记。保留目标目录中已有的管理状态；按规范化路径合并项目，同 provider/sessionId 的会话不重复创建。Windows 扩展路径前缀统一为普通路径；保留实际大小写与路径分隔符。
- 项目 ID 合并时复制对应附件、任务偏好及项目默认值到合并后的身份；已存在的目标文件优先。Claude 历史和其索引复制到共同的引擎目录。旧数据库、旧文件及已过时缓存保留在原位置，方便恢复；不复制活动 SQLite 的 db/wal/shm 文件组合。
- 文件复制或数据库约束失败时不标记该源完成，下次启动可重试。完成标记与导入记录在同一事务内；迁移后删除的任务不会在后续重启时复活。
- Web v34 通过数据库触发器维护旧设置、队列等业务表的外键投影。因此桌面端直接创建或删除目录时，Web 的关联写入仍有效。

这属于同机共享存储。远程浏览器使用 Web 服务所在电脑的数据，不在浏览器设备上建立第二份数据库。

公共 Project 暂时保留 `roots` 数组的传输形状，但输入、输出协议均要求恰好一项。两端选择器共用单选函数，选择新文件夹会替换旧选择。Git worktree 仍是任务的执行工作区，不增加项目根目录。

新目录的身份为独立生成的 `project-<UUID>`，任务外键、路由和设置关联均使用该 ID；路径唯一约束只负责防止同一文件夹重复注册。仓储保存磁盘真实路径并保留大小写和平台分隔符，不能保存仅用于比较的路径键。路径修复不得更换项目 ID。

Codex 适配边界负责翻译请求、响应、通知和审批请求中的任务引用。正文、工具文本和回合 ID 保持原值；不同 provider 的 session ID 不共享映射。适配器只为 Codex 任务执行请求，其他 provider 必须接入自己的执行适配器。

### 任务标题与首条消息预览

正式名称与首条输入预览独立保存。首次向未命名的 Codex 任务发送请求时，两端先持久化首个非空输入行（最多 1024 个 Unicode 字符），无正文时使用技能或附件名称。预览只写一次，后续消息不改写它，也不改变任务排序时间。列表、固定任务、详情和搜索按“正式名称 → 持久预览 → 新聊天”显示；预览不能冒充引擎协议的 `name`，因此自动标题成功后仍能替换预览，手动改名仍保持优先。

Web 与桌面共用 `local-catalog-schema.json` 中的 `previewSql`，通过独立的 `managed_task_previews` 表保存预览，删除任务时由外键一并清理。建表是幂等增量操作，兼容任一端先升级；不改变既有任务表的列顺序或管理字段。

旧版本遗留的空标题任务在打开本地仓储时恢复：仅针对已有 Codex 会话绑定、正式名称和持久预览都缺失的记录，以只读方式按 session ID 查询原生索引中的有界预览。基线索引为 `state_5.sqlite`，目录使用 `CODEX_SQLITE_HOME`、`CODEX_HOME` 或默认 `~/.codex`；源索引缺失、占用或不兼容时保留离线目录能力，下次打开重试。恢复不导入或复活任务，不读取完整会话、不调用模型、不更改正式名称、排序、置顶或归档状态。正常列表读取不轮询执行引擎。

## 首次迁移

1. 读取原目录、活动任务、归档任务以及既有 Web 项目记录。仅首次导入需要上游列表接口。
2. 对目录路径规范化、去重；多文件夹目录拆成多个单文件夹目录。首个目录保留旧 ID，其余使用确定性的路径派生 ID。
3. 任务按原目录范围中的最长匹配工作路径归属；worktree 等不匹配路径保留原主目录归属。原独立聊天继续保留独立作用域。
4. 保留旧任务 ID 作为应用 ID，同时登记原 session ID，避免破坏现有链接与任务附件。新任务开始使用独立应用 ID。
5. Web 在同一事务迁移任务偏好、队列和异步问题的作用域；拆分目录复制项目默认值。桌面端复制任务偏好和项目默认值，保留旧文件以便失败重试。
6. 记录与完成标记同时提交。分页错误、约束失败或文件复制失败不会标记完成；成功后重启不再从上游重建目录或覆盖本地名称。

删除应用目录只移除应用记录及相关状态，不删除用户磁盘文件夹。显式归档、恢复或永久删除任务则优先使用底层 Agent 的开放能力，成功后再更新应用记录；应用独占的临时任务工作区继续按现有安全边界清理。

### 归档、恢复与永久删除

| 引擎                     | 归档与恢复                                                                           | 永久删除                                                                          |
| ------------------------ | ------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------- |
| Codex                    | 使用原生 sessionId 调用 `thread/archive`、`thread/unarchive`，同步底层历史的归档状态 | 调用 `thread/delete`，清理原生历史后移除应用任务及关联状态                        |
| Claude Agent SDK 0.3.316 | 未开放会话归档接口，保留应用本地归档及恢复，历史不删除                               | 调用官方 `deleteSession(sessionId, { dir: cwd })`，再清理应用历史、附件和任务记录 |

Codex 能力依据为 [官方 App Server 文档](https://developers.openai.com/codex/app-server#api-overview)及项目固定的 0.166.0 协议；归档和删除可能同时处理原生派生子会话。Claude 能力核对 [官方 TypeScript SDK 参考](https://code.claude.com/docs/en/agent-sdk/typescript)与已安装 SDK 的公开类型：`deleteSession` 明确删除本地会话正文及子代理正文目录，当前没有 `archiveSession` 导出。

Web、移动浏览器和桌面遵循相同顺序：先校验任务归属及运行状态，再调用底层能力，最后提交本地管理状态。无原生会话绑定的空任务只操作应用记录，不为管理操作创建会话，也不要求引擎在线。Codex 仅在官方 RPC 明确返回方法不存在（`-32601`）时回退本地操作；断连、超时、权限或其他错误会保留本地记录供用户重试，不能作为“不支持”处理。已删除原生会话的精确 not-found 响应允许完成剩余本地删除。

旧版本仅在本地归档的 Codex 会话，恢复时可能得到“没有归档历史”的原生响应；适配器会按原生 ID 读取元数据确认会话仍存在后再恢复本地状态，不读取完整正文。旧导入会话在真正恢复执行时仍保留按需 unarchive 的兼容路径。整个流程不新增后台同步、轮询或逐任务启动预热。

早期本地迁移若把 macOS/Linux 的路径比较键写成小写反斜杠路径，启动时会根据原 Codex 目录恢复正确路径，同时保留本地项目 ID、名称、任务和设置。修复只在检测到这种异常时读取原目录，正常启动不重新同步上游管理状态。

## 接入其他引擎

新的执行适配器使用同一 LocalCatalogStore 契约，设置自己的 provider 与 sessionId，并在执行边界处理身份和通知。目录、任务列表、名称、置顶和数据库迁移继续由应用管理；任务归档、恢复、永久删除在本地目录边界协调底层开放能力，不得只因本地写入成功就报告原生操作成功。

## 验证

- `packages/server/src/local-catalog*.test.ts`：持久化、稳定分页、目录唯一性、迁移拆分与回滚、身份映射，以及引擎离线时的 HTTP 管理全流程。
- `local-catalog-preview.test.ts`、`local-catalog-title-restart.test.ts` 与 Rust `local_catalog::preview_tests`：自动标题成功、失败和取消后的重启恢复，旧仓储升级补齐，以及正式名称、归档和排序保持。
- Rust `local_catalog` 测试：本地生命周期、创建空任务不发送 RPC、执行请求与通知身份转换。
- 单文件夹协议测试和共享选择器回归：拒绝多个根，不丢弃用户输入中的额外根后继续创建。
- 两端运行完整测试、类型检查、静态检查及构建；浏览器验证通过 chrome-devtools-mcp 连接运行中的 Chrome。

删除 Web 旧计划时，SQLite Worker 在同一事务中回收确实从快照移除的 web 配置和附件。不会全表清扫，因此其他来源和不属于旧快照的私有配置保持。任一步失败会回滚整个事务。

桌面端先写入 `acp_scheduled_retirements` 删除意图，再发布旧格式 JSON，最后按原修订号清理配置与意图。意图只保存来源、ID 和修订，最多 1000 项。重启时根据权威 JSON 判断：计划仍在则撤销意图，计划已删除则回收匹配修订的配置；较新配置不会被旧意图删除。清理失败保留意图，在下一次加载或删除时重试，不增加后台轮询，也不删除生成的任务及其历史。私有表不改变旧 JSON、目录版本或旧配置格式。

### 新 ACP 计划定义（开发中，内部端口）

`acp_scheduled_plans` 独立保存新计划的项目身份、名称、提示词、规则和原始 ACP 引擎配置。`acp.plan.read/set/delete` 按来源和 ID 区分，创建使用修订 0，更新 / 删除匹配修订；更新不能更换项目。最多 1000 项、单项 512 KiB、总计 32 MiB。它不写旧计划 JSON、旧配置或共享目录版本；定义存储完成不代表新调度器已经接入，现阶段不开放用户入口。

TypeScript 契约位于 `acp-scheduled-plan.ts`，原生 Node Worker 使用保留 TypeBox 符号的生成 JS。修改契约后运行 `pnpm exec tsx tools/generate-acp-plan-schema.ts` 并格式化生成文件；测试会核对完整契约（含符号）一致。Rust 在实际数据库边界校验相同定义，双端共用正反例、SQL 和容量限制。运行阶段、附件资源事务及新建 UI 继续接入。

### 新计划运行状态（开发中，内部端口）

`acp_plan_state` 保存定义修订、下一次时间及状态修订。`acp.plan.arm` 要求同时匹配定义与状态修订；定义更改后旧游标不能领取。`acp.plan.claim` 在立即事务中检查启用、到期、修订及占用，推进游标并写入 runId 和定义快照；身份冲突或损坏定义使整次事务回滚。

`acp_plan_runs` 的 claimed / unknown 阶段阻止再次领取、改定义及删除。`acp.plan.finish` 按预期阶段 CAS 保存明确结果或未知结果，不自行重发；调用者必须先核对既有持久提交账本。未知保留快照，明确 started / failed 释放快照，每计划最多保留 20 项运行记录。`readState` / `readRun` 可在重启后恢复状态。没有超时自动释放或新增轮询，旧计划 JSON 与版本号不变；正式执行器及用户入口仍待接入。

### 新计划索引与到期发现（开发中）

`acp_plan_index` 由定义写入触发器事务维护，升级时回填已有定义。索引只含名称、项目、引擎、启用状态和规则，单项投影最多 16 KiB，不含提示词与原始配置。`acp.plan.list` 按来源 / ID 分页；`acp.plan.due` 从时间索引读取已武装、已启用且定义修订匹配的到期项，排除 claimed / unknown，每批最多 100 项。续查游标使用 `(nextRunAt, scheduleId)`，调用方结束一轮后从头开始下一轮，避免错误计划占满批次时使后续正常项饥饿。

双端调用式发现复用已有 RRULE / 时区计算器，在数据库事务外计算后再 CAS 领取，单项失败不推进游标，已结束规则写空下一次时间。当前没有后台轮询，也未连接实际 ACP 执行器；应先接入附件资源和持久提交核对，再启动生产调度。

索引初始化完成后写入私有完成标记，之后打开目录不再扫描定义表回填；定义修改由事务触发器同步。索引表被重建时清除该标记并重新回填，进程在回填与标记之间退出也可幂等恢复，不改旧 user_version。最终检查发现重复打开时扫描定义表的潜在开销，已采用这一初始化边界减少读取。

### 新计划纯文本执行（开发中）

双端调用式执行器先将 claimed 原子转为 unknown 获得唯一发送权，再进入 ACP。提交键按来源及计划 / 运行身份散列，目录、配置修改和进程重启不会改变该次输入身份。Node 复用持久 submitTask CAS，Native 复用稳定任务创建、acp.submission.prepare 与现有 prompt.start 命令；不写旧 turnOptions 或读取旧模型。

只有新的占用者能发送；其他调用仅核对账本，缺失、准备中或未知记录均不能作为重发证据。已确认结果优先于当前目录 / 认证恢复；缺失的任务引用可由已有账本或稳定任务目录找回，同时保持 unknown。明确未提交写 failed，断线和无法落账保持 unknown。Node 服务只装配显式 ACP / 持久仓储下的调用入口，没有新增自动调度。当前附件 / skills 在任务创建前拒绝，新建 UI、资源交付和后台循环仍待接通。

### 新计划资源存储（开发中，内部端口）

`acp_plan_resources` 与 `acp_plan_resource_chunks` 独立保存元数据和原始二进制，不使用旧版会随快照清理的 `scheduled_task_attachments`。令牌绑定来源、计划和项目；追加按偏移和块摘要校验，完全相同的块可重试。单块最多 256 KiB，Node Worker 使用 `Uint8Array`，Native 使用类型化 `Vec<u8>`，字节不经 JSON / Base64。封存逐块检查连续性与 SHA-256，文本还校验 UTF-8；读取检查块摘要和元数据尺寸，损坏时明确失败。

暂存最多 3000 项 / 128 MiB，绑定最多 20000 项 / 512 MiB。单资源文本最多 1 MiB、图片 10 MiB、文件 50 MiB；同计划图片最多 20 张 / 50 MiB，其他附件合计最多 50 MiB。预算按声明的总大小预留，不能靠未上传完毕绕过；未绑定资源超过 24 小时后由下一次暂存回收，不新增轮询。绑定资源不按时间过期。

创建或完整编辑资源计划使用 `acp.plan.save`，在同一立即事务中核对定义修订、项目身份、全部附件引用及封存状态，再提交定义、资源绑定和旧资源回收。CAS 冲突或运行未解决时返回空结果；预算或绑定错误会全部回滚。计划删除通过外键级联回收资源及分块，不改变旧计划 JSON、共享 `user_version`、旧配置或已生成的历史任务。

这些端口仍是内部存储能力，不接受任意前端路径。授权上传暂存、每轮缓存恢复、资源执行与新建界面尚待装配，当前执行器仍拒绝附件，不能把资源已落盘视为计划可以执行。
