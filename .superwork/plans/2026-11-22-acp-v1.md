# Feature Implementation Plan

**Goal:** 将 Web 与桌面共用的 ACP Provider 切换为稳定 ACP v1，保留任务及历史身份。

**Suggested Spec Reads:**

- `.superwork/spec/guides/index.md` — 共享实现和验证入口
- `.superwork/spec/core/shared/index.md` — 提交去重、历史恢复和取消隔离
- `.superwork/spec/protocol/shared/index.md` — 原始停止原因与跨端一致性

**Architecture:** 保留 SDK 2.8.0，使用其 v1 入口；核心回合以 prompt 响应结算，历史以 load 响应划界。可选接口按 v1 能力协商，未公布的能力不调用。Web 与桌面继续共用同一运行时。

**Tech Stack:** TypeScript、官方 ACP SDK、Vitest、pnpm、Bun 宿主编译。

## Global Constraints

- 关键逻辑使用清晰中文注释；流式事件保持背压与有界缓存。
- 保留任务 ID、原生 session ID 和旧磁盘格式；发送结果未知时禁止自动重试。
- 不新增逐 token 持久化或全量历史复制。
- 协作登记：acp-v1-20261122 / codex-acp-v1。

## 根因复核与撤回补救

- 用户指出未找出根因就增加三次重试不合理；撤回 `task-runtime-binding.ts` 的 150/300ms 退避和三次重读，同时撤回相关测试及共享规范，恢复原有首屏读取行为。
- 对三个真实 ACP v1 冷会话跟踪 `readTaskWithCheckpoint`：第一次读取各收到一次 `acp.session.updated`，使结构版本从 0 变为 1；服务端原有第二次读取结构版本稳定并成功。该现象本身不能解释最终 503。
- 对 3210 上六个较大任务（对应原生历史约 5.5–13.3 MB）直接单次读取快照，全部 HTTP 200，耗时约 0.17–3.46 秒。该验证不经过前端重试。
- 撤回后的绑定与 checkpoint 回归 19 项通过，Web 重新构建成功，并重启本次拥有的 3210 实例载入撤回结果。
- 原始 503 尚未稳定复现，没有足够边界证据定位其产生原因；不把暖缓存成功或后续读取成功当作根因修复证明。此次只完成撤回未经充分证实的补救，不能声称历史加载问题已根治。

## ACP v1 冷加载 503 根因与修复

- 本机 Web 六个旧任务中四个首读返回 `TASK_SNAPSHOT_BUSY`。隔离启动带诊断的同版 Web，在四个真实冷会话上复现两次读取均被 `acp.session.updated` 判定为快照过期。失败在截止时间前发生，事件发布先于快照同步捕获。
- 共享检查点在同步捕获时核对快照中的 ACP 会话状态是否与最新完整状态一致。相符时检查点可覆盖这些通知，旧状态、缺失状态、其他结构事件仍按原条件处理。
- RED：`pnpm exec vitest run packages/core/src/task-snapshot-checkpoint.test.ts` 的完整状态用例因返回 `TASK_SNAPSHOT_BUSY` 失败。GREEN：相同状态只读一次，状态不符仍返回繁忙。最终 Core、ACP Provider 和 Web 快照一致性共 72 个文件、372 项通过，7 项按现有可选条件跳过。
- `pnpm typecheck`、`pnpm lint`、`pnpm lint:architecture` 和 `pnpm build:node` 通过。性能 15 项通过，macOS 桌面编译宿主 12 项通过。
- 隔离 Web 冷启动后，四个原失败任务均在首次请求返回 HTTP 200、历史正文和 ACP 会话状态。本机 3210 更新到修复构建并重启后，原始六个旧任务均在首次检查返回 HTTP 200 和历史正文。桌面验证覆盖共享代码与编译宿主。
